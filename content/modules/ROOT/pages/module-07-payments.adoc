= Lab 7 — Onboard Payments within platform boundaries

include::partial$environment.adoc[]

**Objective of this lab/demo:** Show how ACM assigns an existing fleet cluster to a team and maintains its application, resource-budget and access boundaries. Continue into real Azure identity self-service after the allocation is understood.

**Time:** 8 minutes for steps 1–3; steps 4–5 are an optional configuration-only explanation. **Personas:** platform administrator and Payments developer. **Starting state:** Payments prepared on `{destination-cluster}`; baseline Compliant, application Healthy. Preparation and cleanup are in the xref:appendix-facilitator.adoc[facilitator runbook]. Use the xref:session-60-minutes.adoc[one-hour session] to combine this with identity, placement and operations.

This session uses the presenter's administrator login to inspect the design. A real developer console login requires configured IdP groups and tested console permissions; that integration is not currently demonstrated. Admin access and hidden menus do not prove tenant isolation. Restricted-token API tests from rehearsal are supporting evidence, not a live human-login claim.

== 1. Show the team's allocation

Open **ACM → Infrastructure → Clusters → {destination-cluster} → Labels** and point to `demo.acm.example.com/payments=true`.

Use **ACM → Search → `kind:Placement namespace:acm-demo-payments name:payments-team`** for governance allocation. Inspect its selector and exact allowed cluster. Then use `kind:PlacementDecision namespace:acm-demo-payments`; choose only the hub objects labelled `cluster.open-cluster-management.io/placement: payments-team` and inspect `status.decisions`.

There is a second `payments-team` Placement in **`{gitops-namespace}`**, consumed by the ApplicationSet. Do not confuse these two namespace-qualified resources. Both should select the spoke; decisions are hub objects, not workloads on that cluster.

**Say:** “This existing cluster is allocated to Payments. The platform controls which cluster is eligible; the team does not choose arbitrary destinations.”

**Expected:** Only the approved spoke is selected. **Value:** Repeatable allocation within fleet controls. **Fallback:** Inspect the Placement YAML and cluster labels if the decision view is delayed. This allocates an existing cluster; the xref:attachment$self-service-payments-cluster-request.example.yaml[cluster-request example] is an illustrative contract, not a working ARO creation API. CAPA/CAPZ provisioning is a separate extension, outside this one-hour session.

== 2. Inspect the centrally maintained boundaries

Open **Governance → Policies → payments-team-baseline**, namespace `acm-demo-payments`. Inspect spoke results and related ResourceQuota, LimitRange, NetworkPolicies, Role and RoleBinding for `acm-demo-payments`.

Use **ACM Search** with `kind:Role namespace:acm-demo-payments name:payments-developer` and `kind:RoleBinding namespace:acm-demo-payments name:payments-developer`. Select the **spoke** result, inspect its actual verbs, resource kinds and subjects, and compare them with the baseline policy's desired objects. If Search cannot expose the object, use the policy's related-object details/YAML as the fallback.

**Say:** “The platform defines the team's resource budget and access rules centrally. Developers manage permitted application resources in their namespace; they do not change quotas, identity bindings or cluster-wide controls.”

**Expected:** Compliant baseline and bounded namespace rules. **Value:** Delegation without cluster-admin. **Fallback:** Show related-object YAML. Do not broaden permissions merely to make a console page visible. Exact-name hub API permissions do not imply access to fleet-wide console listing.

== 3. Show application delivery within the boundary

Open **ACM → Applications → acm-demo-payments**: this is the ApplicationSet row. Then use **ACM Search → `kind:Application namespace:{gitops-namespace} name:payments-{destination-cluster}`** to inspect the generated hub Application. Verify destination `acm-demo-payments`, public source path `payments`, automatic sync and Synced / Healthy status.

Use `kind:AppProject namespace:{gitops-namespace} name:acm-demo-payments` to inspect its repository, destination and resource-kind allowlists. If Search does not index AppProject, show the xref:attachment$gitops-payments-resources.yaml[checked-in definition] or open the signed-in Argo CD Route as described in the xref:module-03-gitops.adoc[GitOps guide]. No manual sync is needed for this already automatically reconciled application.

**Say:** “ACM selects the cluster; GitOps delivers the reviewed application. The platform controls where and what this project can deploy.”

**Expected:** payments-api Synced / Healthy. **Value:** Developers consume a prepared deployment path. **Fallback:** Inspect sync conditions and the generated Application. Do not manually deploy a second workload and present it as ACM/GitOps delivery.

This sample uses synthetic data and does not process payments or call Azure. Git repository permissions and branch protection are separate controls. The central Argo controller is shared and trusted; this is not a separate-controller-per-tenant architecture.

Continue to xref:module-08-azure-access.adoc[approved Azure access] now for the one-hour customer story. That module creates an actual identity, federation and scoped grant and proves data access. The following two steps are optional and are not part of the main session.

== Optional 4. Detect identity configuration drift

Open **Governance → payments-workload-identity → {destination-cluster} → violation details**. Inspect desired ServiceAccount `payments-runtime` in `acm-demo-payments` and its missing approved client-ID annotation.

**Say:** “ACM reports where the workload identity configuration differs from the platform contract.”

**Expected:** Inform / NonCompliant while the application stays healthy. **Value:** Central drift visibility. **Fallback:** Inspect the desired and related objects; if already Compliant, explain that the prerequisite reset was not performed rather than removing a live identity during the session.

This isolated example uses a nonfunctional all-zero client ID. A compliant annotation does not prove an Azure identity, federation or role assignment exists.

== Optional 5. Remediate from ACM

Choose **payments-workload-identity → Actions → set remediation to Enforce**. If unavailable, edit the root Policy YAML and set `spec.remediationAction: enforce` (and its embedded ConfigurationPolicy remediationAction to the same value). Save without changing the approved identity value or scope.

Watch this named policy become **Compliant**, then use **ACM Search → `kind:ServiceAccount namespace:acm-demo-payments name:payments-runtime`** to inspect the spoke annotation. If unavailable, show policy-related objects and the desired YAML. Do not treat a compliant placeholder annotation as Azure access.

**Say:** “The platform owner authorizes the correction once; ACM applies it on the selected cluster. This is configuration remediation. Next we will show the full Azure dependency chain.”

**Expected:** Annotation restored; app and baseline remain healthy. **Value:** Central, scoped remediation. **Fallback:** Inspect ConfigurationPolicy messages and cluster availability. Do not claim Azure access was established.

Continue with xref:module-08-azure-access.adoc[approved Azure access], which provisions and verifies a real identity. Repeat-session reset and offboarding are backstage activities in the facilitator runbook.

== Checkpoint

Record the exact cluster, namespace, current status and any skipped step. A saved object alone does not prove reconciliation completed.
