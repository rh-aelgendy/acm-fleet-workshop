= Lab 8 — Request approved Azure access from the hub

include::partial$environment.adoc[]

**Objective of this lab/demo:** Manage identity growth through an approved workload-access contract: inspect ownership and scope centrally, reject excessive access, accept a small request, and follow ACM/ASO reconciliation through real Azure access proof.

**Time:** 12–15 minutes plus Azure propagation. **Starting state:** platform prerequisites prepared. Choose a fresh-request track (plan AwaitingRequest / NotRequested) or an existing-request track (plan Provisioned with current access proof). The fresh submission creates real Azure resources and incurs the module's normal charges. Choose this track during preparation; do not enable an unprepared cloud integration in the meeting.

This is a custom request contract, not a built-in ACM service catalog. The request is pre-approved by template/admission rules; there is no human approval queue. A presenter using admin credentials demonstrates the workflow, not a developer SSO boundary. xref:appendix-facilitator.adoc[Preparation and cleanup].

**Identity inventory scope:** this centrally governs identities represented by the platform's ASO resources and ACM policies. It does not automatically discover or govern every managed identity in an Azure subscription. Client IDs are public identifiers; Azure credentials and private token material are never shown. The independent `payments-workload-identity` policy uses a placeholder and is not the real access proof in this lab.

== 1. Show the platform's control point

Open **ACM → Governance → Policies**, filter namespace `acm-demo-payments-catalog`. Find:

* `payments-approved-access-plan`: approved request and Azure resources on the hub.
* `payments-approved-azure-workload`: identity configuration and reader on the spoke.
* `payments-approved-access-verified`: successful access proof.

In **ACM Search**, use `kind:ConfigMap namespace:acm-demo-payments-catalog name:payments-access-plan` and select the **hub** result. Open its details/YAML. The reliable local alternative is **hub console → Workloads → ConfigMaps → project acm-demo-payments-catalog → payments-access-plan → YAML**.

Show `accessProfile`, `allocatedCluster`, `workloadNamespace`, `federatedSubject` and `azureRole` when the request is provisioned. Compare this contract with the three named ACM policies; leave their existing Enforce/Inform modes unchanged.

**Say:** “The team asks for a capability. The platform supplies the identity, scope and federation without handing over Azure credentials.”

**Expected:** Fresh track: AwaitingRequest / NotRequested. Existing track: ApprovedTemplateReady / Provisioned. **Value:** A central, inspectable workflow. **Fallback:** If already provisioned, present the existing outcome and skip new submission; do not withdraw access merely to recreate a starting slide.

== 2. Demonstrate the approved input boundary

First check **hub console → Workloads → ConfigMaps → project acm-demo-payments-requests** for `payments-access-request`.

* **Request absent:** open **hub + → Import YAML**, paste the complete xref:attachment$self-service-approved-access-request-denied.yaml[denied request], and click **Create**. It requests `subscription-owner`; creation must be rejected.
* **Request present:** open **payments-access-request → YAML**, change only `data.accessProfile` from `payments-blob-reader` to `subscription-owner`, and click **Save**. The named admission rule must reject the update. Discard that unsaved editor change and reopen the resource to confirm the stored profile is still `payments-blob-reader`. Do not delete the working request.

**Say:** “The team cannot turn a Blob reader request into subscription ownership.”

**Expected:** Rejection naming `acm-demo-payments-approved-request`; no accepted override. **Value:** Constrained self-service. **Fallback:** A Forbidden response from RBAC or an AlreadyExists response is not proof of the admission rule. Use **ACM Search → `kind:ValidatingAdmissionPolicy name:acm-demo-payments-approved-request`** for the hub admission definition, or the xref:appendix-azure-design.adoc[platform YAML]. Preserve the current working request if its edit cannot be demonstrated.

== 3. Submit the approved request through the console

For a fresh run, use **hub + → Import YAML** with the complete xref:attachment$self-service-approved-access-request-approved.yaml[approved request]:

[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: payments-access-request
  namespace: acm-demo-payments-requests
  labels:
    demo.acm.example.com/id: aro-retail
data:
  application: payments-api
  environment: development
  accessProfile: payments-blob-reader
----

Click **Create**. If the exact approved request already exists, inspect its three stored values instead of creating a duplicate; its prior provisioning is the existing-request track. Open the plan ConfigMap again and follow `requestState: ApprovedTemplateReady` / `azureState: Provisioning` toward **`azureState: Provisioned`**. “ApprovedTemplateReady” does not change to “Provisioned”; these are different fields.

Saving this request is the only live trigger. ACM's already-installed policies and ASO reconcile continuously; there is no presenter-side submit script. If Azure is still progressing after a few minutes, continue the GitOps placement section and return to this proof before closing.

**Say:** “No client ID or role ARN is copied by the team. The controllers derive and reconcile the approved resources.”

**Expected:** Request accepted and plan advances. **Value:** Small user input with repeatable automation. **Fallback:** Read ACM policy messages and the plan's current state. Accepted is not the same as provisioned.

== 4. Inspect the Azure dependency chain

Use **ACM → Governance → payments-approved-access-plan → Results / template details / related objects** to inspect the ASO resources on the **hub**. Use these exact ACM Search queries if the custom kinds are indexed; otherwise keep the related-object view and show the desired xref:attachment$self-service-approved-access-aso-resources.example.yaml[ASO definitions]. An absent custom-kind Search result does not mean Azure provisioning failed.

[cols="1,1",options="header"]
|===
|Hub query / resource
|Evidence to point to
|`kind:UserAssignedIdentity namespace:acm-demo-payments-catalog name:payments-api`
|Ready=True with observedGeneration matching metadata.generation; platform-owned identity
|`kind:FederatedIdentityCredential namespace:acm-demo-payments-catalog name:payments-api-spoke`
|Verified spoke issuer, exact subject `system:serviceaccount:acm-demo-payments-cloud:payments-blob-reader`, audience `api://AzureADTokenExchange`
|`kind:RoleAssignment namespace:acm-demo-payments-catalog`
|Follow only the assignment named in this policy; UUID name, Storage Blob Data Reader role, Payments container scope
|`kind:ConfigMap namespace:acm-demo-payments-catalog name:payments-identity`
|ASO-exported clientId, principalId and tenantId; public IDs, not passwords
|===

Then search **`kind:ServiceAccount namespace:acm-demo-payments-cloud name:payments-blob-reader`**, select the **spoke** result and compare its `azure.workload.identity/client-id` annotation with the exported hub client ID. In the reader Deployment, inspect the workload-identity Pod label and serviceAccountName. Follow `payments-approved-azure-workload` to see that ACM wires the approved identity to this selected workload, rather than copying an Azure credential into Git.

Use ACM policy related objects if navigation differs. Do not open operator Secrets.

**Say:** “ACM maintains the approved desired resources. ASO makes the Azure API changes and returns identity identifiers. ACM uses them to configure the selected workload.”

**Expected:** Current Ready conditions and plan `azureState: Provisioned`. **Value:** Auditable dependencies and automatic identity wiring. **Fallback:** Inspect ASO conditions; allow Azure propagation. A stale Ready condition or a green configuration-only policy does not prove data access.

== 5. Prove both allowed and denied access

In **ACM Search**, find `kind:Deployment namespace:acm-demo-payments-cloud name:payments-azure-reader`. Follow it to the spoke console → Pod → **Logs**. Look for:

* `ready: true`
* `approvedContainerHTTP: 200`
* `otherTeamHTTP: 403`
* `otherTeamError: AuthorizationPermissionMismatch`

Return to **Governance → Policies → namespace acm-demo-payments-catalog → payments-approved-access-verified → Results** and inspect compliance with the request present. This policy checks reader availability. The reader's readiness probe is tied to its own 200/403 checks; the policy does not independently call Azure. Current logs are the detailed data-plane evidence.

**Say:** “We check the real access outcome, including denial outside the approved scope. An annotation alone would not prove this.”

**Expected:** Reader available and verification policy Compliant with the request present. **Value:** Operational evidence of least-privilege access. **Fallback:** If the private spoke console is unreachable, show ACM's Deployment availability and verification policy, and label detailed logs as rehearsal evidence. Network errors are not a passing authorization denial. After reset, Compliant means correct absence, not working provisioned access.

Leave the request in place for discussion. Withdrawal removes the demo workload, identity, federation and role assignment; do that afterward using the facilitator runbook. xref:appendix-azure-design.adoc[Implementation, scopes and production boundaries].
